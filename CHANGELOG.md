## [11.0.0-preview.2] — unreleased

### Breaking

- SQL in a declaration is stored as segments, format `v` 3: text, and each column by its property path. A model snapshot scaffolded with `11.0.0-preview.1` is refused with a message that says so; remove the migrations scaffolded with the preview and scaffold them again ([#178](https://github.com/CaffeinatedCoder/CodoMetis.EFCore.SchemaKit/issues/178)).
- `Predicate` and `KeyTarget.Template` hold a `SqlTemplate` and are no longer made from a string. In the contract, `SchemaResolver.Template` takes a `SqlTemplate`, and `SchemaJsonWriter` and `SchemaJsonReader` have `Template` and `OptionalTemplate` ([#178](https://github.com/CaffeinatedCoder/CodoMetis.EFCore.SchemaKit/issues/178)).
- A lambda in a declaration becomes SQL when its model is finalized, and is checked where it is written as before. Until then `GetDeclarations`, `FindDeclaration` and `Redeclare` hand out the declaration as it was written, and `SqlTemplate.IsBound` is false for its lambdas. Two declarations without a name that are written differently and are the same SQL are refused when the model is finalized, where they were refused at the second call ([#179](https://github.com/CaffeinatedCoder/CodoMetis.EFCore.SchemaKit/issues/179)).
- In the contract, `SqlSpelling` is an abstract class a provider's package derives its spelling from, and `SqlSpelling.PostgreSql` is gone: the kernel holds no spelling. PostgreSQL's is `PgSchema.Spelling`, for a package that takes lambdas for PostgreSQL declarations of its own ([#184](https://github.com/CaffeinatedCoder/CodoMetis.EFCore.SchemaKit/issues/184)).

### Added

- B-tree and unique indexes on PostgreSQL, declared with `DeclarePostgres(pg => [pg.BTree(…), pg.Unique(…)])`: a key is a property or an expression, and `pg.Key(…)` gives it `Desc()`, `NullsFirst()` or `NullsLast()`; `where:`, `include:`, `name:`, and `nullsDistinct:` on a unique index. `GetDeclarations<PgIndex>()` reads them back. A renamed index is renamed in place and anything else about one is a drop and a create ([#202](https://github.com/CaffeinatedCoder/CodoMetis.EFCore.SchemaKit/issues/202)).
- Hash, GiST, SP-GiST, GIN and BRIN indexes: `pg.Hash(…)`, `pg.Gist(…)`, `pg.SpGist(…)`, `pg.Gin(…)` and `pg.Brin(…)`, each with the options PostgreSQL has for its method and no other. A key takes an operator class of its method with `Ops(…)`, and a key of text a collation with `Collate(…)`. Storage parameters are `fillFactor:`, `deduplicateItems:`, `buffering:`, `fastUpdate:`, `pendingListLimit:`, `pagesPerRange:` and `autosummarize:`; one out of PostgreSQL's range is refused where it is written, and a changed one is a drop and a create. One of PostgreSQL's own operator classes on a column whose type does not take it is refused when the migration is scaffolded. A GiST key on a scalar column gets `btree_gist` from the migration ([#204](https://github.com/CaffeinatedCoder/CodoMetis.EFCore.SchemaKit/issues/204)).
- `concurrently: true` on every index method builds the index with `CREATE INDEX CONCURRENTLY`, outside the migration's transaction. It is for the create alone, and an index that differs only in it is the same index: no migration. `migrations script --idempotent` over a migration with such a statement fails with the index named and writes no script, since PostgreSQL refuses the statement in the script's `DO` block (25001) and psql would record the migration without its index; a plain script, a bundle, `database update` and `Migrate()` run it. The statement's `migrationBuilder.Sql(…)` call carries the annotation `CodoMetis:SchemaKit:Object` with the index it is for. In the contract, `ISchemaDialect.WhyNotOutsideTransaction` says which ways of applying a migration do not carry a statement written with `suppressTransaction: true` ([#206](https://github.com/CaffeinatedCoder/CodoMetis.EFCore.SchemaKit/issues/206), [#155](https://github.com/CaffeinatedCoder/CodoMetis.EFCore.SchemaKit/issues/155)).
- A declaration on a type of a TPC hierarchy is an object in that type's table and in the table of every type derived from it, where it was refused. A name the declaration states is the declaring type's table's, and a derived type's copy is `{name}_{table}`; a default name has its table in it ([#187](https://github.com/CaffeinatedCoder/CodoMetis.EFCore.SchemaKit/issues/187)).
- A 5.x snapshot with an exclusion constraint on a type of a TPC hierarchy is read, and the same model declared with SchemaKit scaffolds no operations, where the snapshot was refused. A snapshot scaffolded before 5.5.0 stays refused, with the way off it ([#189](https://github.com/CaffeinatedCoder/CodoMetis.EFCore.SchemaKit/issues/189)).
- A declaration on an entity split over two tables (`SplitToTable`) is created in the table that has the columns it reads, where one on a column of the second table was refused. One that reads a column of each table is refused ([#191](https://github.com/CaffeinatedCoder/CodoMetis.EFCore.SchemaKit/issues/191)).
- A property compared with a value is written as the column stores that value: an enum as its number or its name, a property with a value converter through the converter, a `bool` stored as text, a `DateTime`, a `Guid`. An enum comparison and a `DateTime` or `Guid` in a comparison were refused ([#180](https://github.com/CaffeinatedCoder/CodoMetis.EFCore.SchemaKit/issues/180)).

### Changed

- On SQLite, a migration that would create a declared object on a table it also rebuilds is refused when it is scaffolded, with the declaration and the table named. It applied and left the database without the object, or failed when it was applied. Neither package creates objects on SQLite; this is for a contributor written against the contract ([#145](https://github.com/CaffeinatedCoder/CodoMetis.EFCore.SchemaKit/issues/145)).
- On SQLite, an object on a table that one migration renames and rebuilds is seen by the rebuild: it was passed over when the operation that makes the rebuild named the table as it was before the rename, and the migration applied without the object ([#193](https://github.com/CaffeinatedCoder/CodoMetis.EFCore.SchemaKit/issues/193)).
- Both packages are built against EF Core 11.0.0 and `Npgsql.EntityFrameworkCore.PostgreSQL` 11.0.0, and depend on `[11.0.0, 12.0.0)` of them ([#174](https://github.com/CaffeinatedCoder/CodoMetis.EFCore.SchemaKit/issues/174)).
- Whether a column in a condition can be null is the model's answer, not the C# annotation's: `IsRequired()` on a `string?` leaves the null compensation out, and `IsRequired(false)` on a `string` puts it in ([#180](https://github.com/CaffeinatedCoder/CodoMetis.EFCore.SchemaKit/issues/180)).
- The expression and the condition of an exclusion constraint read from a 5.x snapshot are SQL written by hand: the constraint is taken to read every column of its table ([#178](https://github.com/CaffeinatedCoder/CodoMetis.EFCore.SchemaKit/issues/178)).

### Fixed

- A 5.x snapshot with an empty list of exclusion constraints on a type of a TPC hierarchy is read as holding none, where one scaffolded before 5.5.0 was refused as if it held constraints ([#171](https://github.com/CaffeinatedCoder/CodoMetis.EFCore.SchemaKit/issues/171)).

## [11.0.0-preview.1] — 2026-11-17

The first preview, for `net11.0`, EF Core 11 with `Npgsql.EntityFrameworkCore.PostgreSQL` `11.0.0-rc.3`, and PostgreSQL 16 and 18. It declares exclusion constraints only: indexes, SQL Server, SQLite and the rest are [not in it yet](https://github.com/CaffeinatedCoder/CodoMetis.EFCore.SchemaKit/blob/main/README.md#what-it-does-not-do-yet). The stored form of a declaration in a model snapshot is not final in a preview, and a later preview may ask for the migrations to be scaffolded again. That does not change a database already built, so a database built from a preview is one to build again; the permanent promise starts at `11.0.0` ([#9](https://github.com/CaffeinatedCoder/CodoMetis.EFCore.SchemaKit/issues/9)).

### Added

- `CodoMetis.EFCore.SchemaKit`, the kernel: `UseSchemaKit()` puts SchemaKit's model differ and SQL generator around EF Core's in every path that turns a model into DDL, and refuses a context where something else displaced them ([#40](https://github.com/CaffeinatedCoder/CodoMetis.EFCore.SchemaKit/pull/40)).
- `CodoMetis.EFCore.SchemaKit.PostgreSQL`: `UseNpgsql(…, o => o.UseSchemaKit())`, and exclusion constraints declared with `DeclarePostgres(pg => [pg.Exclusion(…)])`, with lambda elements and conditions, a deferral and a name ([#25](https://github.com/CaffeinatedCoder/CodoMetis.EFCore.SchemaKit/issues/25)). `Overlaps` takes a range or a multirange (an array or a list of `NpgsqlRange<T>`); a plain array does not compile, since PostgreSQL has no GiST operator class for one ([#104](https://github.com/CaffeinatedCoder/CodoMetis.EFCore.SchemaKit/issues/104)).
- `btree_gist` is installed by the migration that first needs it, unless the model declares it or calls `SuppressBtreeGistInjection()` ([#25](https://github.com/CaffeinatedCoder/CodoMetis.EFCore.SchemaKit/issues/25)).
- A model snapshot of `EFCore.ComplexIndexes` 5.x with exclusion constraints is read, and the same model declared with SchemaKit scaffolds no operations; a snapshot with 5.x's indexes or temporal constraints is refused ([#93](https://github.com/CaffeinatedCoder/CodoMetis.EFCore.SchemaKit/issues/93), [guide](https://github.com/CaffeinatedCoder/CodoMetis.EFCore.SchemaKit/blob/main/docs/moving-from-complexindexes-5x.md)).
- An operation of a migration 5.x scaffolded that only 5.x's SQL generator rendered is refused, not applied as another object ([#110](https://github.com/CaffeinatedCoder/CodoMetis.EFCore.SchemaKit/issues/110)).
- `GetDeclarations<T>()`, `FindDeclaration<T>(name)` and `Redeclare<T>(…)` read and amend what a model declares ([#45](https://github.com/CaffeinatedCoder/CodoMetis.EFCore.SchemaKit/issues/45)).
- A name two objects of one model take is refused as `SK1001`, every collision at once ([#96](https://github.com/CaffeinatedCoder/CodoMetis.EFCore.SchemaKit/issues/96)).
- A declaration is refused where it is written when the context's options do not register the package that renders it, as with `UseNpgsql(…).UseSchemaKit()` in place of `UseNpgsql(…, o => o.UseSchemaKit())`; and the PostgreSQL package beside a kernel of another version is refused by `UseSchemaKit()` with both versions ([#113](https://github.com/CaffeinatedCoder/CodoMetis.EFCore.SchemaKit/issues/113)).
- The contributor contract other packages declare objects through, experimental (`SK9001`) until `rc.1` ([#7](https://github.com/CaffeinatedCoder/CodoMetis.EFCore.SchemaKit/issues/7)).
- Each GitHub release carries a CycloneDX SBOM per package, which lists what a consumer of the package takes on ([#35](https://github.com/CaffeinatedCoder/CodoMetis.EFCore.SchemaKit/issues/35)).
